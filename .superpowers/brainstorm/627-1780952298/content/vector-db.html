Vector DB döntés: Qdrant vs ChromaDB

A Codex RAG retrieval és a manuscript semantic memory alapja — ez az adatbázis keresi vissza a releváns karaktereket, helyszíneket, lore-t az AI promptokhoz.

A

Qdrant Eredeti terv

Rust-alapú, production-grade vector DB. Saját HTTP API, Qdrant Cloud opció, self-hosted Docker image, szűrőkkel és payload metadatával.

Előnyök

  • Gyors és memória-hatékony
  • Gazdag filter API (project_id, entity_type stb.)
  • Qdrant Cloud = zero infra a prod deployban
  • Jól dokumentált Python kliens
  • Docker image egyszerű

Hátrányok

  • Külön service a Docker Compose-ban
  • Qdrant Cloud havidíj (~$0 free tier)
B

ChromaDB

Python-natív, egyszerűbb vector DB. Beágyazható (in-process) vagy self-hosted szerver módban futtatható. Fejlesztői DX-re fókuszált.

Előnyök

  • Embedded mód: nincs külön service
  • Python-natív, könnyű setup
  • Gyorsabb fejlesztői iteráció

Hátrányok

  • Nincs managed cloud opció (self-host kell prod-ba)
  • Kevésbé érett production workloadra
  • Filter API gyengébb mint Qdrant
  • Skálázhatóság kérdéses nagy projekteknél
C

pgvector (PostgreSQL kiterjesztés)

A PostgreSQL-hez adott vektor kiterjesztés — így egyetlen DB-ben van a strukturált adat ÉS a vektoros retrieval. Neon PostgreSQL natívan támogatja.

Előnyök

  • Nincs külön vector DB service
  • Neon-on azonnal elérhető
  • JOIN-ok strukturált adattal egy queryben
  • Kevesebb infrastruktúra
  • MVP-hez bőven elég teljesítmény

Hátrányok

  • Nagy korpusznál (~1M+ vektor) lassabb mint Qdrant
  • Kevésbé fejlett filter/facet API
  • Ha kell Qdrant, migráció szükséges
Ajánlás a hibrid architektúrához

MVP-hez: pgvector (C) — egy service-szel kevesebb, Neonon ingyen fut. V1-ben migráció Qdrantra ha a retrieval minősége vagy a sebesség kérdéses lesz. A model router és a retrieval service legyen elég absztrakt hogy ez később cserélhető legyen.
